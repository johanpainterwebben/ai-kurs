# Plan: CI/CD – från push till `main` till ny version på servern

Datum: 2026-11-17. **Steg 1–4 och 6 genomförda 2026-11-28** (se "Genomfört" sist). Steg 5 väntar på Svelte. Det här är den enda planen för CI/CD och
driftsättning. Den ersätter det som stod om driftsättning i
[atgardsplan-kodanalys-2026-10-28.md](atgardsplan-kodanalys-2026-10-28.md) (steg 7, `deploy.yml`) och
samlar de CI/CD-fynd från granskningarna 2026-10-28 som fortfarande är öppna (se tabellen nedan).

## Mål

När kod pushas eller mergas till `main` ska ett jobb på servern starta av sig självt. Jobbet hämtar den nya
versionen, startar den, kontrollerar att den fungerar och går tillbaka till den förra versionen om den inte
gör det. Ingen ska behöva logga in på servern för att driftsätta.

## Beslut

- **Servern hämtar själv (pull).** Servern har inga öppna inkommande portar, så GitHub kan inte skicka
  något dit. En tjänst på servern frågar registret med jämna mellanrum om det finns en ny godkänd image.
  Med en kontroll varje minut startar jobbet på servern inom ungefär en minut efter att publiceringen är klar.
  Ingen kod från GitHub körs på servern, och servern behöver bara läsrätt till registret.
- **Servern bygger ingenting.** "Uppdatera koden" betyder att servern byter till den image som CI redan
  byggt, testat och skannat. Det som körs är då exakt det som testades, och servern behöver varken Go,
  Node eller källkoden.
- **Omstarter och API-villkoren:** Appen hämtar från temperatur.nu direkt när den startar. En driftsättning
  ger därför ett extra anrop, och en driftsättning som rullas tillbaka ger två. Det är godtagbart
  (beslut 2026-11-17), så femminutersregeln behöver inte klara en omstart innan driftsättningen
  automatiseras. Driftjobbet ser i stället till att det stannar vid högst två extra anrop per ny version
  (se Steg 4). Undantaget gäller bara omstarter vid driftsättning. Efter fel och krascher ska
  API-villkoren fortfarande följas.
- **Alternativ som valdes bort:** en self-hosted GitHub Actions-runner på servern. Den startar jobbet direkt
  och syns i GitHub, men den kör workflow-kod från repot på servern med Docker-åtkomst, alltså i praktiken som root.

## Flödet

```
push/merge till main
  └─► GitHub Actions
        ├─ ci:      gofmt, vet, test -race, benchmark, govulncheck, lint, Docker-bygge + Trivy
        └─ publish: (bara om ci lyckas) bygg → Trivy → signera → publicera på GHCR
                    taggar: <commit-SHA> (ändras aldrig) och main (pekar på senaste godkända)
                          │
                          ▼
servern (timer var minut)
  └─ driftjobbet
       1. lås (bara ett jobb åt gången)
       2. vilken digest pekar taggen main på? samma som nu → klart
       3. kontrollera signaturen (rätt repo, workflow och gren) → annars avbryt och larma
       4. spara nuvarande digest som "föregående"
       5. hämta och starta den nya (docker compose up -d)
       6. vänta på healthy + /healthz
       7. fel → starta föregående igen och larma
       8. logga resultatet
```

## Steg

Varje steg är tänkt som en egen PR.

### Steg 1 – Bara godkänd kod publiceras (F1)

| Fil | Ändring |
|---|---|
| `.github/workflows/ci.yml` | Kan också anropas från andra workflows (`workflow_call`). |
| `.github/workflows/publish.yml` | Anropar `ci.yml` och publicerar bara om alla jobb lyckas (`needs:`). |
| Inställningar på GitHub | Regel för `main`: ändringar via PR, Go/Lint/Docker måste vara gröna, ingen force-push. |

### Steg 2 – Publicering som servern kan lita på (F1, F8)

| Fil | Ändring |
|---|---|
| `.github/workflows/publish.yml` | Taggarna `<commit-SHA>` och `main`. Imagen signeras med cosign utan nyckel (GitHub OIDC); bara det jobbet får `id-token: write`. SBOM och provenance bifogas. Imagen som skannas är den som publiceras. |
| `Dockerfile` | Basimagerna låses med digest (`@sha256:…`). Dependabot föreslår uppdateringar. |

### Steg 3 – Compose för drift i stället för bygge (F9)

| Fil | Ändring |
|---|---|
| `docker-compose.yml` | `image: ${IMAGE}@${DIGEST}` i stället för `build: .`. Imagens namn och digest kommer från en env-fil på servern, så att varken konto eller namn hamnar i git. Ingen publicerad port. Resursgränser (`mem_limit`, `pids_limit`, `cpus`). |
| ny: `compose.build.yml` (eller liknande) | Lokalt bygge för utveckling: `docker compose -f docker-compose.yml -f compose.build.yml up --build`. |

### Steg 4 – Driftjobbet på servern

| Fil | Ändring |
|---|---|
| ny: `deploy/pull-deploy.sh` | Skriptet i flödet ovan. Generiskt: alla värden (imagens namn, katalog, larm, tidsgränser) läses från en env-fil på servern. `set -euo pipefail`, `flock`, inga hemligheter i loggen. |
| ny: `deploy/pull-deploy.service`, `deploy/pull-deploy.timer` | Exempel på systemd-enheter: timern körs varje minut, och tjänsten är härdad (`NoNewPrivileges`, `ProtectSystem`, `PrivateTmp`). |
| `DEPLOY.md` | Avsnittet om CI/CD och steg 8 skrivs om: så installeras jobbet, så rullar man tillbaka för hand, så ser man loggen. Bara generiska uppgifter och platshållare. |
| Serverrepot (inte här) | Env-filen med de riktiga värdena, en token som bara får läsa paket (`read:packages`), larmkanalen och installationen av timern. |

Skydd i skriptet:

- **Signaturen kontrolleras före varje start.** En image som inte är signerad av det här repots
  publiceringsjobb på `main` startas aldrig.
- **Högst två extra anrop mot temperatur.nu per ny version:** en start av den nya versionen och, vid fel,
  en återställning. Kommer flera pushar tätt efter varandra startas bara den senaste godkända versionen.
- **Ingen loop av omförsök.** En version som har rullats tillbaka försöks inte igen förrän det finns en
  ny commit. Annars skulle varje försök ge ett nytt anrop mot API:et.

### Steg 5 – Frontend (när webbsidan har flyttats till Svelte)

| Fil | Ändring |
|---|---|
| `.github/workflows/ci.yml` | Nytt jobb: `npm ci`, `svelte-check`, lint, `npm audit`, bygge. |
| `Dockerfile` | Ett byggsteg för frontend före Go-bygget. Ingen Node i den färdiga imagen. |

## Säkerhet

- GitHub kan inte nå servern, och inget öppnas för det. Servern ansluter bara utåt till registret.
- CI har inga hemligheter utöver `GITHUB_TOKEN`. Publiceringen har dessutom `packages: write` och `id-token: write`.
- PR:er och forkar kan inte publicera eller driftsätta: `publish` körs bara på `main`, och servern startar
  bara imagar som är signerade från `main`.
- Serverns token får bara läsa paket och ligger i env-filen på servern (`chmod 600`), aldrig i git.

## Verifiering

- En PR med ett test som fallerar ger ingen ny image.
- En push till `main` når servern inom några minuter. Loggen visar den nya digesten och `healthy`.
- En avsiktligt trasig version (t.ex. `/healthz` som inte svarar) rullas tillbaka och ger ett larm.
- En osignerad image med rätt tagg startas inte.
- Loggen över anrop till temperatur.nu visar högst två extra anrop per ny version, även när den rullas tillbaka.

## Öppna frågor

1. **Larm:** Hur ska du få veta att en driftsättning har rullats tillbaka? E-post, en push-tjänst eller bara den externa övervakningen?
2. **Hur ofta servern frågar:** Varje minut (snabbt) eller var femte (färre anrop mot registret)?

## Genomfört (2026-11-28)

- **Ett workflow i stället för två.** `publish.yml` är borttagen. Jobbet *Publicera och signera* ligger i
  `ci.yml` och väntar på Go, Lint och Docker med `needs:` (fynd F1). Då körs inte kontrollerna två gånger
  vid varje push, vilket `workflow_call` hade gett.
- **Signering** med cosign utan nyckel (`id-token: write` bara i publiceringsjobbet). Taggarna är
  `<commit-SHA>` och `main`, och digesten står i körningens sammanfattning.
- **Compose** kör `image: ${IMAGE_REF}` låst till digest, med `pull_policy: never`. Det lokala bygget
  ligger i `compose.build.yml`.
- **Driftjobbet** finns i `deploy/` (`pull-deploy.sh`, systemd-enheter och `deploy.env.example`), med
  installation i DEPLOY.md, steg 11. Skriptets logik är testad med låtsasversioner av `docker` och
  `cosign`: första versionen, samma version igen, en version som inte blir frisk (återställs och försöks
  inte igen), fel signatur och en ny bra version.
- **Inte gjort:** låsa basimagerna med digest (F8), resursgränser och att ta bort den publicerade porten
  (F9), samt larm (valfri `NOTIFY_URL`). Själva körningen i GitHub och på servern kan inte testas härifrån.
